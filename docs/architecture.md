# Architecture decisions

## Deployment

The plan's container assumption is superseded by a rootless systemd user service because Docker daemon access is unavailable. Node 22 + npm 9 run an Express 5 API and the built React/Vite UI in one process. PostgreSQL 18 is provisioned by an administrator; the application role owns only its dedicated database. No host config or privileged operation is part of the installer. The only application listener is hardcoded to 127.0.0.1. `PUBLIC_ORIGIN` is an exact browser write-origin allowlist, not a bind address.

## Identity boundary

`server/domain.ts` contains the provider-neutral `identity` adapter. The configured local Caddy gate verifies identity and injects `X-Hermes-Verified-Email`; the adapter normalizes and allowlists that email, which also identifies the single household. The gate must strip/overwrite inbound headers. Loopback isolates remote clients but cannot isolate other trusted-host processes. There is no claim that locally forged admitted headers are cryptographically detected. No password or cookie/session storage exists; financial browser writes require an exact Origin. Production fails closed without configured identity; development bypass is explicit and forbidden in every other environment. Production refuses labeled demo households. UI/static assets are gated too; the service worker caches only a nonfinancial offline shell and icon.

A future OIDC adapter can map verified issuer/subject to the local owner context. The existing email-only gate does not supply an immutable subject; changing email is an explicit identity migration. Every read and mutation resolves the authorized household and uses its key or follows an already checked household-owned resource. Composite foreign keys reject cross-household ledger/category/account references. The MVP supports exactly one configured admitted owner per process.

## Financial model

Money is signed integer minor units with safe-integer checks at the boundary, BIGINT in PostgreSQL, and two-decimal currencies only. Account balance equals opening balance plus nonvoid account entries. Positive means asset value; a negative card balance means debt. Transfers have exactly two opposite entries for the stated amount and no splits. Expenses have one negative account entry; income/refunds have a positive entry. Expenses/refunds have strictly positive category split amounts totaling the parent amount. Expenses count positively and refunds negatively toward category spending. A linked refund must reference a household expense.

Transactions, entries, splits and allocations are append-only. The only permitted posted-transaction mutation is a reasoned, audited void before reconciliation; stable IDs remain reserved on voids. Reconciled periods reject backdated entries and voids. Database deferred triggers enforce complete ledger shape at commit, including modifications attempted by inserting extra child entries later. Audits are append-only. Each financial API write claims idempotency and commits side effects, audit and response atomically. Same-owner advisory locks serialize writes, with unique row constraints as the final safety boundary. There is no separate pending committed idempotency state: an uncommitted claim waits/rolls back with its transaction.

Targets are keyed by explicit calendar year, month allocations by first-of-month date. Target edits include before/after audit, while additive allocation records preserve adjustments. Categories have fixed rollover behavior; it cannot rewrite historical months. Rollover crosses years; reset categories release surplus/deficit to unassigned at the next month. Starting funds are explicit and independent of opening account balances. Income adds unassigned funds, allocations consume them. Future allocations affect unassigned only through the viewed month. Annual planned/actual totals cover the whole selected year; current available balances cover the selected month. Targets warn and never constrain writes. No hidden balance clamping occurs.

Effective financial dates are ISO calendar dates, not UTC-midnight instants. Database timestamps are timestamptz UTC instants; household timezone is validated and stored. CSV dates are interpreted as explicit calendar dates using the mapping. Browser displays activity dates without UTC conversion. The server supplies today in the household timezone for initial month and transaction defaults, falling back to the browser date only before household setup. Automated period close is not part of this MVP: reconciled account periods lock ledger history, and fixed category rules protect rollover history.

## Imports

Profiles are immutable schema-versioned mapping settings. A new profile creates a new mapping version rather than overwriting one used for prior imports. UTF-8 text content SHA-256 plus canonical settings hash is unique per household/account. Parser output stores normalized transaction fields (not the raw source row/file), fingerprint, row number, error and duplicate type. Original filenames are retained as text and rendered escaped by React. Stable identity is unique on account/source/external ID even after void. Empty IDs are SQL NULL. Fingerprints are not globally unique.

Every row has an explicit accepted/skipped/not-duplicate decision; malformed and stable-ID duplicates require skip, probable matches require explicit keep-as-distinct or skip. Source collisions discovered after preview fail the entire commit rather than being silently skipped. Committed batches return their prior result and decisions. Re-preview of identical settings/content returns the same review/complete batch. No financial writes happen at preview. Raw text exists transiently during parsing only. Browser state is memory-only; neither API data nor imported files enter the service-worker cache/local storage.

Positive imported inflows are income because a CSV alone cannot reliably distinguish refunds or transfers. The review UI/documentation explicitly requires those rows to be skipped and recorded with the correct manual type. A mapping can assign one default expense category; per-row recategorization and merchant rules are later features.

## MVP boundaries and release gates

Implemented: onboarding, multiple accounts, categorized/split manual activity, linked refunds, card purchases/payments, targets, uneven additive allocations, rollover/reset, warning-only overruns, account statement comparison, reconciliation period locks, audit browsing, CSV mappings/preview/review/history, idempotency, exports and deployment artifacts. No fake values appear outside an explicitly seeded demo.

Initial reconciliation compares all account activity through a date, rather than offering individual clearing marks. Transactions are corrected through voids/reversing entries, rather than in-place edits. There is no automatic month-close workflow, generic OIDC login, bank sync, multiuser sharing, cross-currency ledger or full portable application export. The UI supports two split categories, the API up to 100. The intended single-household MVP currently loads all household activity for calculations; pagination/server aggregates are required before very large histories.

Release gates still require connected API/PostgreSQL concurrency tests, an actual trusted Caddy spoof-header check, browser interaction/accessibility checks on devices, and an operator backup/restore/reboot drill. The supplied plan's complete acceptance criteria remain the product target; this implementation is not claimed as a verified public-distribution release.
